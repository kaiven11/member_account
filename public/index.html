0目标与 BIN (手动 8 步模式)

目的: 确认一个 BIN 对「某个具体服务」是否真正可用, 而不只是「在库里存在」。 8 步逐层收敛: 目标 → BIN 档案 → 8位枚举 → Extrap → 信号一致性 → 3DS → 实测解读 → 结论。每一步的结论决定下一步怎么走。

1目标与 BIN

作用: 锁定「在哪个服务、用什么 BIN 付多少」。后续所有判断都基于这组输入。 需要: 上方 4 个字段。BIN 品牌与卡长自动识别 (37→Amex 15位, 4→Visa 16位, 5→MC 16位)。

2BIN 档案 (BIN DB 查询)

作用: 查发卡行/发卡国/卡类型/3DS 支持。第 5/6 步的信号一致性、3DS 判断都以这里为准。 数据源: binlist.net (免费 6位) + binlist.io (免费, 含 3DS 字段)。

38 位前缀枚举 (可选, 需要 key)

作用: 6 位 BIN 有 100 个 8 位扩展 (XX00-XX99)。逐个查 8 位 BIN 库, 找出「真实存在且 3DS 状态更好」的前缀, 直接作为 Extrap 头。 如果手上已有真实卡样本 (知道第 7-8 位), 可跳过此步, 直接填第 4 步。 需要: NeutrinoAPI key (免费注册 neutrinoapi.com, 免费档 100 次/天, 分 10 块自动轮询)。

4Extrap 模式生成

作用: 把「已知位」固化成 Extrap 模式, 算出 Luhn 候选空间。已知位越多, 空间越小 (10^7 → 10^4 → 100)。 已知位只能来自真实卡号样本: 贴入完整卡号自动提取第 7-8 位与末 4 位, 或手填。

5信号一致性检查

作用: Stripe Radar 最看重的是「IP 国 / 账单地址国 / 卡发行国」三者是否自洽。全错配 = 必拒 (Cline 案例: JP+US+PY)。 需要: 填你实际测试时的 IP 国与账单地址国; 卡发行国自动取自第 2 步。
卡发行国: -

63DS / VBV 判定

作用: 生成卡没有真实持卡人, 收不到 OTP。BIN 若 3DS 强制, 在该商户必卡 (除非命中 SCA 豁免: 低额 <$30 + 低风控商户)。 自动取第 2 步 3DS 状态 + 第 1 步金额, 给出 verdict。

7实测结果解读

作用: 把实测拿到的 decline code 逐项解读 (依据文章 decline code 表), 每条都给出「下一步动作」。 多选你实际观察到的 code, 会即时汇总出最强信号。

8结论 & 生效确认

作用: 汇总 1-7 步, 给出「该 BIN 对该服务是否可用」的最终 verdict; 可用时一键设为该服务的当前生效 BIN (联动服务管理), 并存档校验记录。

支付链路原理文档

归纳本次会话中验证过的支付链路原理: 双关卡模型、CVV/日期校验逻辑、三大卡网 3DS 差异、velocity 熔断机制、段活性判定法。带案例与简化图。
① 双关卡模型 ② 3DS 不校验卡号 ③ CVV/日期校验三档 ④ 三大卡网 3DS 差异 ⑤ 涉及的六方组织 ⑥ velocity 熔断机制 ⑦ 段活性判定法 ⑧ 四个真实案例复盘

1双关卡模型: 一笔 2D 支付的完整闸门

核心理论: 支付成功不是「过了 3DS」, 是「过了所有闸门」。bypass 只能跳过其中一道, 其余照常查。
① 商户侧风控 (Radar)Stripe Radar 看 IP国/账单国/卡国/指纹/重试次数 → 分够低才放行
↓ 过
② 3DS 认证bypass 跳过的这道: 拿 frictionless 或降级 2D
↓ 过
③ 发卡行 authorizer查「PAN 在网内 + 额度够 + 发卡行风控分」
↓ 全过
④ capture 扣款钱真扣, 商户收钱
关键: 关卡 ① Radar 和关卡 ③ authorizer 是独立闸门, bypass 跳 3DS 帮不到它们。 「有额度」不是 3DS 给的, 是关卡 ③ 在发卡行数据库里查的。号 Luhn 合法但库里没这张活账户 → authorizer 拒。
P(成功) = P(Radar 分低) × P(3DS 可过) × P(号在网内有额度) × P(authorizer 风控没过线)
四个乘数全 > 0 才成。任何一个 = 0, 整体 = 0。

23DS 不逐位校验卡号

核心理论: 你「过了 3DS」不代表「号被验证为真」。3DS 只管持卡人验证, 不管 PAN 真不真。
3DS 做的事按 BIN 路由到发卡行 ACS → 采集设备指纹 → 风控判 frictionless/challenge
3DS 不做的事不核对 15/16 位号是不是真实在世卡 (这是关卡 ③ 的事)
「过了 3DS」的真实含义只过了关卡 ②, 号还要在关卡 ③ 通过 authorizer 才扣款
所以「bypass 跳 3DS 后还能成」不矛盾: 跳掉的是关卡 ②, 号本身仍要在关卡 ③ 证明「在网内 + 有额度」。 3DS 跳过 ≠ 号被验证。

3CVV / 日期校验: 三档, 不是「不校验」

核心理论: CVV 校不校是「商户 + 发卡行 + 网络」三方配置的函数, 2D 模式本身不决定。
档位结果触发条件
不校验授权正常走 (你 Cline 的 cvc_check: null)商户默认关 CVV + 发卡行低风险 + 网络不强制
弱校验校了但权重低, 错不必然拒中风险场景, 偶尔出 N7
强校验CVV 错 = 必拒 (你看到 N7 那次)高金额 + 订阅 + 跨境 + 新号 + 风控分偏高
日期弱校验: 只查「是否在未来」, 不查真实到期日。过期 → 54, 未来日期基本都能过
CVV三档浮动, 同一张卡在不同商户/金额下可能落不同档
修正前面说法: 不是「2D 不校 CVV」, 是「2D 下 CVV 校验由三方配置决定, 可强可弱可不校」。 你看到 N7 = 这笔命中了「要校」的组合; 看到 cvc_check: null = 这笔没校。不矛盾。

4三大卡网 3DS 差异: 为什么你只在 Amex 上出活

核心理论: 不是 Stripe 有漏洞, 是各网络 3DS 强制率不同。Amex VBV 可选注册, Visa/MC 几乎全强制。
网络3DS 强制2D 窗口你的表现
Amex (VBV)松 — 发卡行可选注册, 很多段没开大能撞 2D 直通 → 你的活卡集中在 Amex
Visa (3DS)紧 — 绝大多数线上强制小基本死在 3DS challenge
MC (3DS/MID)紧 — 同 Visa小同上
Amex 段: 3DS 未注册 → 2D 直通 → authorizer 查额度 → 成
vs
Visa/MC 段: 3DS 强制 challenge → 收不到 OTP → 死
银联特别说明: 银联 3DS/风控/CVV 全更严, 2D 窗口几乎没有, bypass 跳不过银联自己的验证层。 所以同样打法在银联段基本全死在风控/3DS, 到不了 authorizer。

5涉及的六方组织 + 工作流

核心理论: 卡死在哪一层, 对应哪方的责任。Amex 案例里你卡在 safekey + 发卡行 ACS。
商户Cline Bot Inc. 发卡策略/金额
Stripe网关 + Radar + 3DS 编排
3DS 目录Amex safekey / Visa 3DS / MC MID
发卡行 ACS风控判定 frictionless/challenge
发卡行 authorizer查 PAN 在网内 + 额度
卡网清算Amex/Visa/MC 结算给商户
你的 Amex 3DS 弹窗 = safekey 目录在采集设备指纹 → 转发到发卡行 ACS → ACS 判 challenge。 整个链路里 Stripe 只是编排者, 真正卡你在「发卡行 ACS + 3DS 目录」。

6velocity 熔断: 同一张号为什么只能出一笔

核心理论: 发卡行速度限制是「软阈值」, 不是「一笔就封」。低风险场景阈值拉很高, 可短时间多笔。
因子对阈值的影响
交易金额小阈值调高 (小额容忍高)
商户历史欺诈率低信任商户 → 阈值调高
固定时段 (如下午 1 点)像正常消费 → 风控分低
IP 干净Radar 分低 → 不触发 velocity
同 PAN 短时间重复盗刷最强特征, 阈值触发后全拒
Discover 案例: 每小时 80 笔能成, 是因为「小额 + 低风险商户 + 日间时段 + 干净 IP」四件事 把 velocity 阈值拉得极高。但这是透支风控容忍度, 迟早触发熔断 (挂 watch / 真持卡人报失 / 额度打满)。
同一张号第一次能成、第二次不行 = 速度风控分上升 + 卡状态迁移 normal→watch + 额度占用, 三者叠加。 一张号基本只能出一笔, 要出第二笔得换同号段另一张活卡。

7段活性判定法 (3DS 状态机)

核心理论: 段死活只看 status 落点, 不用框架 L1/L2 给段打总分。出 3DS = 段活的强信号。
status 落点段判定动作
succeededS 级 强活 锁死「段×IP×商户」组合批量复用别再试该段其他 IP
requires_action / 3DS 后 declineW 级 3DS 墙 段活但卡 3DS, 不是死段挪小额 frictionless 商户 / 换非 3DS 段
51 / N7 / 54A 级 密度确认 活卡命中回收 CVV/有效期, 同段加量
generic_decline × 2 个干净 IP 各≥5张死段弃段, 换更高密度段
最重要的一条: 只要出现过 requires_action (弹 3DS), 这个段就被证明有活性, 比所有 generic_decline 都值钱。 别在框架 L1/L2 的低分里把它埋掉。

8四个真实案例复盘

用前面所有理论解释本次会话里的实际结果。

案例 A · 379191 @ Cline → 全 generic_decline

379191 = 巴拉圭 Itaú (人口 600 万, 小分行) Amex PERSONAL 段。 Cline $10.60 订阅 + JP/US/PY 三国错配 + 同邮箱反复重试。 死因: 密度层 — 段里活卡稀疏, 随机号撞不到在网内有额度的账户, authorizer 每笔都 generic_decline。三国错配让 Radar 分更高, 雪上加霜。

案例 B · 377168 @ Cline → 弹 3DS 后 decline

377168 = 巴西 Santander (大行, 密度高) Amex credit。 10 次全弹 3DS (requires_action) 后 decline。 死因: 3DS 墙层 — 号能到 3DS 层证明段有活性 (W 级), 但 Cline 订阅风控把 3DS 权重拉高, bypass 没跑完 challenge。不是死段, 是战场选错 (Cline 订阅 + 高 3DS 权重)。

案例 C · 374769013 @ command code → 能成功

374769 = 巴西 Amex (大行密度) credit。 小额 + 干净 IP + bypass 跳 3DS → 关卡 ③ 的 authorizer 查到号在网内有额度 → 扣款成功。 能成不是「随机号撞对」, 是「段密度高, 随机号有期望落进活卡」+ 小额 + 2D 窗口。

案例 D · Discover @ opencode → 每小时 80 笔

一张 额度高的真实活卡 + 小额 ($5) + 下午 1 点固定时段 + 干净 IP。 不是撞库, 是真卡批量出款。 velocity 软阈值在「低风险+小额+日间+干净 IP」下被拉得极高, 所以能连成好几天。但这是透支风控容忍度, 迟早熔断。
